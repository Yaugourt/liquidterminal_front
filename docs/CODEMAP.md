## Data source reliability

- **Robust:** LT backend (local DB) `/liquidations/*`, `/staking/*`, `/market/*`; Hypurrscan (fees, spotUSDC, holders, deploys); DefiLlama bridge; HL official API/RPC.
- **Unstable:** Hypedexer `/indexer/*` (402s) — vaults detail, priority-fees, hip4, builders depend on it; every dependent chart must degrade gracefully (fallbacks exist in vaults; priority-fees has schema-drift unwrappers).
- **HypeDexer credits:** billed `2 + ceil(rows/10)` per REST call. Since 2026-09-28 the backend caches every `/indexer/*` read under a key holding every param, so a page's cost is shared by its visitors instead of paid by each; the backend logs `HypeDexer credits (last minute)` per upstream path. Read [`HYPEDEXER_CREDIT_AUDIT.md`](./HYPEDEXER_CREDIT_AUDIT.md) (measured costs per page before/after, rules, re-measure method) before adding or changing any `/indexer/*` call, `limit` or poll interval.
- Backend dev runs on `:3002` (`/home/yanis/LiquidTerminal_Back`), CORS hardcoded to `localhost:3000`. Without it, most values render `$0.00`/`—` but layouts still render (useful for visual-check).
- `pnpm run start` on the backend serves the compiled `dist/`, **not** the source. After pulling backend commits, `pnpm run build` first — otherwise new routes 404 and the symptom looks like a frontend path bug (cost a debugging round on 2026-09-10).
- Locally, self-sampled series (`/market/metrics/history`, positioning history) return `[]` until the backend has been up for hours — tiles/charts that gate on history will read as "unavailable" on a fresh start. Not a defect.

## Known quirks (verified in code or memory)

- Spot data: "liquidity" is actually mid-price mislabeled; duplicate token names → match by `tokenId`; fees window ≈ 10 days. Market caps: Unit-bridged tokens report the underlying's whole supply (shown "—"); HL counts supply parked on a token's HyperEVM system address (`0x20` + index) as circulating — minted there at genesis (XAUT0, USDT0, kHYPE, AXL: 80 tokens) or moved there by the token's single genesis holder (AAPL, MSFT…: 23) — so the backend's `SpotBridgeReserveService` (genesis read once per token, Redis `spot:bridge-reserve:v1`, balances every 5 min) subtracts it and `/market/spot` rows carry it as `bridgeReserve` (XAUT0 was $770,000B, AAPL $4,250B). Still FDV-like: pre-mints held by an issuer's own address (USDE, TRX1).
- HIP-4 backend lists hold the *oldest* markets (upstream order, no sort): anything recent is read by id — deep links, settlement names (`docs/HYPEDEXER_CREDIT_AUDIT.md` P1.3). Live markets come from outcomeMeta; `buildMergedQuestions` drops the indexer's ghosts of them.
- HIP-4 `/indexer/hip4/analytics`: the backend caps `coin` at 256 chars (zod) and `limit` counts rows across **all** coins of a request. Live-market volumes (~450 coins) are therefore batched in `fetchHip4OutcomeVolumes` and cached 5 min in `useHip4LiveMarkets` (coin-filtered calls skip the backend cache). HypeDexer lists both sides of an ungrouped binary under one `outcome_id` (`[141 Yes, 141 No]`), and `question_id` / `singleton_outcome_id` share one number space: key cards with `hip4QuestionKey`, never with a raw id.
- HL `perpDexs` no longer returns `deployerFeeScale`: it is per asset in `allPerpMetas` (`universe[].deployerFeeScale`), aggregated into `feeScaleRange` by `usePerpDexMarketData`.
- Hypedexer's `l4Book` delta stream is lossy: resting orders can leave the book with no `remove` diff (measured 2026-08-07 on HYPE — 10 of 10 asks the price traded through went unannounced). The backend rebuilds each book from a fresh snapshot every 8 s and prunes levels better than HL's touch; the frontend additionally overlays HL `l2Book` for the top 20. Never treat a purely incremental L4 book as accurate.
- Hyperliquid websocket frames are **batches**: `trades` oldest first, with a ~30-trade snapshot right after (re)subscribing; the explorer RPC (`explorerBlock` / `explorerTxs`) sends a 25-item snapshot newest first, then ~1 item per frame, ~14 frames/s each. Read every item (`lib/hl-trades.ts` for trades: newest trade, tid-deduped merge), never `data[0]` (measured 2026-09-28). HL closes a socket after 60 s without a message for it; `l2Book` snapshots arrive every ~5 s even on a dead coin, so token sockets never idle out. Both api and rpc answer `{"method":"ping"}` with `{"channel":"pong"}`; our `/ws` answers it with `{type: "heartbeat"}`.
- Next `<Link>` prefetches every link that enters the viewport (two RSC requests per new href): rows of a live feed pass `prefetch={false}` (`ModuleTableRow prefetch`, dashboard live cards) — the /explorer feed used to fire ~56 requests/s.
- Hypurrscan holders are huge (HYPE 14.9 MB / 260k addresses + 2.8 MB `stakedHYPE`, USDC ~70 MB), regenerated every ~10 min and served ~4 min later. The browser never downloads them: backend `/market/holders/:token?page&limit` returns one page (largest first, only the top 10,000 can be paged), the holder count, summed balance and whale→retail cohorts. Spot + staked balances are summed per address (merging the maps used to drop ~25k HYPE spot balances and double-count those addresses). Hypurrscan keys holders by on-chain name (UBTC, USDT0) while `/market/spot` lists display names (BTC, USDT_USDC): the backend maps them by tokenId.
- The Sidebar mounts on every page, so its badges (`useSidebarBadges`) must stay cheap: the HYPE price and 24h change come from the HYPE socket (`useHypeDayChange`: last trade + `activeAssetCtx @107` mark / prevDay, identical to `tokenDetails`' values) — never `useHypeOverview` / `useHypeSupply`, which pulled 5.2 MB of `tokenDetails` and the Assistance Fund state every minute on every page (until 2026-10-06). Same rule for the /hype layout's `HypePricePill`. The same `activeAssetCtx` frame also carries `dayNtlVlm` (24h volume, read by `useHypeDayVolume`), `circulatingSupply` and `totalSupply`: read HYPE's live figures off the socket before polling HL for them.
- HL `spotMetaAndAssetCtxs`: the contexts array is not aligned with `universe` — it also lists pairs the universe leaves out (1,005 contexts for 330 pairs on 2026-10-08). Match a pair's context by coin name (`ctx.coin === pair.name`), as the backend's spot poller does (it also names each pair's quote token for `/market/spot`); matching by position gave 259 of 330 pairs another pair's circulating supply (HYPE's directory market cap read $62M instead of $25.8B until 2026-10-08).
- Hypurrscan `/spotUSDC` (184 KB, never compressed) holds one point per UTC day plus the current day's point, rewritten every ~10 min at most (watched 2026-10-09). The backend re-reads it every minute and serves it unchanged at `/market/stablecoins/history` (~40 KB compressed, with an ETag: a 60 s poll that finds it unchanged is a 304 of 0.8 KB); `useSpotStablecoins` reads it there (the browser read Hypurrscan directly until 2026-10-09). The OG tiles read `/market/stablecoins` (latest point + 24h variations) server-side.
- HL `userFillsByTime` returns at most 2,000 fills per response and only keeps a user's fills back to a horizon (the Assistance Fund's reached back to 2026-09-26 17:49 on 2026-10-08, ~12 days): page through a range by time (deduping by tid) and treat a day before the horizon as unknown, never as zero. Until 2026-10-08 the browser read one page per day, so /hype/capital showed $23.6M bought back over 13 days instead of $34.1M. The backend's `AfBuybacksService` reads each completed day whole once, keeps it only if the horizon (read after it) is no later than its start, stores it in Redis (35 days), and paces its background reads to 300 weight a minute (a 2,000-fill page weighs 120 of the IP's 1,200; the backend's pollers already use about half).
- Hyperliquid's info API never compresses its responses (`tokenDetails` HYPE 5.2 MB, `allPerpMetas` 83 KB, `perpDexs` 21 KB on the wire) and POST responses are not in the GET cache: shared in flight only. Poll static HL metadata slowly and share it (see `usePerpDexMarketData`, HIP-4 templates). `tokenDetails` is read through the backend (`/market/token-details/:tokenId`): HYPE's genesis list holds 94k balances (KNTQ 10k, 600 KB) and the app only counts them — the backend serves every scalar field plus `genesisUserCount` / `genesisExistingTokenCount` / `nonCirculatingUserCount`, reads HL at most once a minute per token for everyone, only for listed spot token ids, 20 HL reads a minute at most.
- TWAP: every consumer (`useTwapOrders`, the dashboard cards, the user TWAP table) reads the indexer first — `services/market/order/twap-source.ts`: paged `/indexer/twaps` (last 24 h + running TWAPs up to 170 h), stale "activated" rows dropped, names/prices resolved (spot @N, HIP-3 via allMids per dex), 30 s shared cache (2,757 TWAPs vs 444 on Hypurrscan for the same 24 h, measured 2026-10-03). If the indexer fails, backend `/market/twap` is the fallback: Hypurrscan's ~24 h dump with tokenSymbol/tokenPrice/marketIndex/marketType resolved server-side (fetched once per 15 s for everyone). Indexed rows carry `twap-<id>` instead of a transaction hash.
- zod: import through `@/lib/zod-mini` only (ESLint-enforced). Importing `zod` / `zod/mini` itself gives Turbopack the namespace object, which it doesn't tree-shake (~50 KB gz of schema types + ~40 locales on the dashboard). zod/mini issue messages are the bare "Invalid input" (no locale loaded).
- `/explorer` and `/wiki` have pre-existing visual-check clip failures (mobile/1024) — predate the 2026-06 cleanup.
- `visual-check` needs the dev server + Playwright from gstack (`GSTACK_NODE_MODULES` env or `~/gstack`/`~/.claude/skills/gstack`).
- Wallet analytics (Hypedexer `/indexer/users/:user/performance`): defaults to a **7-day** window (`"window":"7d"`) — pass `start_time` (the `{ lifetime: true }` option) for all-time, otherwise it will not reconcile with `/overview` and `/coins`. `avg_trade_size` is not USD (unit undocumented) and `avg_holding_time_s` is inflated — neither is displayed. `total_fees` is positive for a market maker whose HL fills are rebates (sign ambiguous), so no PnL-minus-fees "net" is derived from it. The exchange-level number is HL `portfolio.pnlHistory` (deposits excluded), which is what the address ribbon shows; `accountValueHistory` deltas are polluted by transfers and must not be labelled PnL.
- HL RPC `userDetails` returns only the last ~300 signed actions (16 s of activity for an HFT wallet) and `userFills` the last 2 000 fills — "recent activity" ratios (wallet archetype) are computed over intents and fills separately.
- HL stamps system rows (TWAP slices, liquidation-engine fills, some `cStakingTransfer`s) with an all-zero hash — `isNullHash` keeps them out of every hash merge / lookup in `services/explorer/address` (they used to collapse into one bogus fill and hide null-hash ledger rows); table rows key on `withRowIds` ids, never on `hash`. Pre-2024-05 `userDetails` actions are tuples (`["withdraw2", …]`), not objects — `actionType()` reads both.
- Digest insights (`walletInsights.ts`): `completed-trades` timestamps are naive UTC (suffix `Z` before parsing); the cadence sample is the last 100 round-trips, so "recent form" compares that sample to the lifetime `win_rate`; the ledger's `subAccountTransfer` / `spotTransfer` / `send` carry `user` = sender and `destination` — direction is resolved against the page address; `0x0…`/`0xf…` are ignored, the HyperEVM bridge addresses (`0x2222…` HYPE, `0x20 00…00 <token idx>`) count as `toEvm`/`fromEvm` and come out of `netCapitalIn` — every flow insight compares PnL with that NET figure (deposits alone mislead when a linked account funds the wallet); liquidation insight takes max(DB, ledger) since the indexer win rate excludes liquidations; Hypedexer `last_activity` is `1970-01-01` for a never-traded wallet and HL answers a zero-filled `portfolio` for any address — both treated as no history; predicted funding is HL `HlPerp` APR, longs pay when positive.
- knip is configured (`knip.json`); `components/common/**` and `components/ui/**` are entry points — their exports are never "dead" (DS primitives kept for future pages).
